# Spring Modulith Best Practices (Spring Boot 4)

This guide describes the recommended setup for **Spring Modulith** projects generated by this skill.

## What the scripts support

Use any project script with:

```bash
node scripts/create-project-latest.mjs my-app com.acme my-app com.acme.myapp 25 web --architecture modulith
```

When `--architecture modulith` is enabled, generated projects include:

- `spring-modulith-starter-core` and `spring-modulith-starter-test`
- `springdoc-openapi-starter-webmvc-ui`
- `ModuleSwaggerConfiguration` for per-module OpenAPI grouping
- API versioning conventions for `/api/v{version}/{module}/...`
- Existing native image support (`native` dependency + `Dockerfile-native`)

## Suggested package layout

```text
com.example.myapp
├── config
│   └── ModuleSwaggerConfiguration.java
└── modules
    ├── catalog
    │   ├── CatalogController.java
    │   └── package-info.java
    └── orders
        ├── OrdersController.java
        └── package-info.java
```

## Swagger/OpenAPI grouping by module

The generated configuration groups endpoints by module package and path.

- Group name: module name (for example `catalog`, `orders`)
- Paths: `/api/v*/{module}/**`
- Package scan: `...modules.{module}`

This keeps each modulith slice discoverable in Swagger UI while preserving one deployable unit.

## Spring Boot 4 path versioning

Use path versioning in controller mappings:

- `/api/v1/catalog/...`
- `/api/v2/catalog/...`

Recommended convention:

- First segment after `/api/` is the version token (`v1`, `v2`)
- Next segment is the module name (`catalog`, `orders`)

This convention aligns with grouped OpenAPI docs and enables clean module boundaries.

## GraalVM native builds

Generated projects already include native support:

- `native` starter dependency
- `Dockerfile-native`
- `docker-compose-native.yml`

Build options:

```bash
./mvnw -Pnative native:compile
# or
docker build -f Dockerfile-native -t my-app-native .
```

For reflective or dynamic features, add runtime hints as needed.
